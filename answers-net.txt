
设备的控制实际上还是对内存的操作。
对设备发送信息，只需要修改对应的内存。
接收设备的信息，硬件检测到对应的内存变化会出现相应的中断。

e1000网卡，发送和接收数据包驱动的实现。关键是理解接收和发送的循环队列工作原理。

接收数据包，初始时，整个队列都分配了空的物理页，等待数据传入。网卡会自动将数据包填到队首的物理页，然后队首指针往后移动，
我们需要做的是在队尾处理数据包。
我认为中断可能同时出现在多个核心，所以对循环队列的读取需要上锁。先获取锁，然后取出队首数据包物理页，放一个新的物理页，修改rx_ring结构体，释放锁，再将数据包传入net_rx解析后释放物理页。这个操作一直进行直到队列为空。

发送数据包，网卡会自动读取队首的数据包，然后队首指针往后移动，我们需要做的是在队尾添加新的数据包。
不过队尾或许存在原有已处理数据包的物理页，需要先释放。同样的队尾指针可能会有多进程同时修改。

实现udp数据的接收。
实现对ip数据包处理，如果是udp协议，并且udp包中端口是已经绑定过的，那么就将数据包放入该端口的缓存队列中，队列最多缓存16个。
实现绑定端口系统调用，我选择用一个结构体数组，存储已经绑定的端口以及该端口的缓存队列。
实现接收udp数据包的系统调用，需要传入一个监听的端口，端口队列如果存在数据则直接获取队列头的数据，否则进入睡眠。

定位一个很坑的bug，居然在内核态中出现中断，0xd应该是读取到非法内存。
``` c
scause=0xd sepc=0x80005206 stval=0x1a
panic: kerneltrap
```
通过土办法输出中间代码，找了很久的bug。大概定位到是nettest.c中ping3测试用例。

nettest.c 在ping3测试用例下，先发送了大量的包，然后fork一个子进程，来接收模拟器的包。
并通过管道向父进程反馈发送了多少包。目的是检测一个端口是否最多缓存16个udp包，将多余的废弃。
而模拟器的代码nettest.py，其逻辑是接收到xv6发送的udp包，就向xv6发送一个内容一样的udp包。

通过中间代码发现中断是在fork的子进程中，但是，出中断的代码是子进程的内核态的代码，很难定位。

最后发现在汇编代码kernel.asm中可以找sepc，这确实是个好东西，内核代码所有指令地址对应的c代码都一一对应。
``` c
  int ksrc = htonl(ip->ip_src); // 大端转小端
    80005206:	01aaa783          	lw	a5,26(s5)
          ((val & 0xff00U) >> 8));
```
定位到是在net.c中sys_recv
``` c
int ksrc = htonl(ip->ip_src); // 大端转小端
```
估计ip->ip_src是不存在的。

sys_recv()是读取一个端口对应循环队列的udp包，当队列为空则睡眠让出cpu
在ip_rx()中，检测到udp包，就在对应端口的循环队列中添加该数据包的地址，并唤醒睡眠的进程。
``` c
if (ip->ip_p == IPPROTO_UDP && bp != &bport_list[NBPORT] && (bp->tail + 1)%NPACKET != bp->head) {
  bp->buf[bp->tail] = buf;
  bp->tail = (bp->tail + 1)%NPACKET;
  wakeup(bp);
}
```

经过一番复盘，发现子进程应该是处于睡眠中，被kill了，但是kill的逻辑实际上是唤醒了进程。
``` c
int
kill(int pid)
{
  struct proc *p;

  for(p = proc; p < &proc[NPROC]; p++){
    acquire(&p->lock);
    if(p->pid == pid){
      p->killed = 1;
      if(p->state == SLEEPING){
        // Wake process from sleep().
        p->state = RUNNABLE;
      }
      release(&p->lock);
      return 0;
    }
    release(&p->lock);
  }
  return -1;
}
```
而进程唤醒后队列仍然是空的，我们期望他不是空的。
``` c
  if (bp->tail == bp->head) {// 无数据 睡眠
    sleep(bp, &netlock);
  }
```
所以需要在进程唤醒后，检测是否被杀死。否则会读取队首的脏数据。
